## v1.0.110: 「既存DBと統合して完全版を作成中」で進捗が見えない問題

- **最新の全端末共通DBが過去の端末別バックアップをすべて統合済み**で、かつ保存日時がそれらより新しいと確認できる場合だけ、共通DB1件を照合する高速経路を追加。保存済みペイロードの `backupMode:'complete-merged-v1'` と各端末の作成日時を確認。**一つでも最新共通DBより新しい端末別バックアップがあれば従来の複数ファイル統合**に戻るため、その端末で新規に追加された研究記録を落とさない。共通DBが無い／壊れている場合も勝手に空バックアップで置き換えず従来の保護を維持。

## v1.0.109: YouTubeのNiji Cloudバックアップが20MBを超える問題

「⚠️ バックアップ未確認：バックアップが20MBを超えました。ローカルJSONを先に退避してください」は **YouTubeに注入された Niji Research Helper の Niji Cloud 全端末同期**が表示していたもので、`niji-archive-db` アプリのpCloud保存とは独立しています。

**原因**：従来、端末のIndexedDB（動画・チャンネル・Wiki・視点ペア）と全端末の最新研究バックアップをマージし、非圧縮JSONが20MiBを超える場合はアップロード前に中断。失敗後も未保存の変更を保持し、次回自動同期で同じ警告を出す挙動でした。

**修正**：完全版JSONが16MiBを超えたとき、全データをgzip圧縮してBase64のJSONエンベロープに梱包して従来の `/v1/backups` ゲートウェイへ送信。未圧縮元JSONの件数や内容を間引かない。圧縮後も20MiBを超えた場合は安全に拒否し、ローカル・クラウドの過去世代を保持します。

- 圧縮バックアップは原文バイト長とSHA-256を保存。復元時にgzip展開、SHA-256、全IndexedDBストアの構造、保存元の端末・オリジンを検証し、不正な状態では変更を一切実行しません。
- クラウドへの新規圧縮保存は、サーバー保存後に再度ダウンロードして解凍・検証が通ってから「保存済み」扱い。POST応答が不明なときもリモートバイトを確認します。
- **旧単一JSONバックアップは読み込み可能**。圧縮形式は旧スクリプトが空のDBとして誤認しないよう別`dbVersion`にし、古いクライアントは読み取りを拒否する設計です。PC/iPhone/iPadで同期する場合は、すべての端末を新しいスクリプトへ更新することを推奨。
- 研究DBのバックアップ専用の対応で、**お気に入り・APIキー暗号化同期のデータ形式は変更していません**。配信検索アプリのD1データやpCloudバックアップには一切触れません。
- 実際のリモートWorkerが新しい圧縮形式を受理するかは、初回の本番同期で確認が必要です。失敗した場合でも端末IndexedDBは消さず、前世代はそのまま残します。手動でIndexedDBを削除・初期化して解決しようとしないでください。
